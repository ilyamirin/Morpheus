Morpheus turns independent marketplace servers into a trusted federation.

Each instance owns its catalog, allowlist, policies, Postgres storage, and API. Matrix/Synapse carries verifiable events, while Morpheus validates the protocol, stores the raw timeline, and builds local projections for the admin, seller, and buyer UIs.

Developer Setup Protocol reference

Protocol principles

2. Operating principles

Local autonomy

Morpheus does not require a central marketplace. Each server decides which instances to trust, which policies to accept, and which projections to show users.

Allowlist instead of global search

Federation is built around the local allowlist. If `fashion.example` is trusted by `books.example`, books can accept and index its catalog and order events.

Matrix as transport

Matrix/Synapse handles room membership, federation transport, and timelines. Morpheus defines only the marketplace namespace, validation rules, and state machines.

Replayable state

Raw Matrix events are persisted, and accepted events become the source for projections. An order lifecycle can be replayed and revalidated without trusting the current projection table.

Secrets stay outside Matrix

Payment secrets, bearer URLs, license keys, credentials, files, and delivery artifacts are not transmitted through `io.marketplace.*`. Events keep only references, hashes, and evidence metadata.

Strict protocol envelope

Every event carries `protocol`, `protocol_version`, `protocol_event_id`, `created_at`, `issuer`, and a typed `body`. Unknown critical fields are rejected.

The mini dev environment lets you verify these principles by hand: seller publication updates the catalog projection, buyer order creation creates a backend-owned Matrix order room, seller lifecycle actions publish events into that room, and the admin UI shows counters and the validation stream. Full runbook: Developer Setup.

Runtime architecture

3. Server architecture

The production surface consists of an Axum backend, Matrix Application Service integration, Postgres projections, and CLI/operator tooling. Inside the workspace, protocol logic and state machines live in pure Rust crates so HTTP, SQL, and Matrix concerns do not mix with validation rules.

Key boundary: `morpheus-core` and `morpheus-protocol` do not depend on Axum, SQLx, Tokio networking, or Synapse.
01HTTP APIadmin / seller / buyer
02PublisherMatrix client API
03Synapse AStransactions endpoint
04Validatorprotocol + context
05Storeraw events + projections
Docker E2E repeats this pipeline three times: `books.example`, `cases.example`, and `fashion.example` each have their own Postgres, Synapse, and Morpheus runtime. nginx federation proxies expose reachable Synapse TLS endpoints on `:8448`, while Morpheus servers are available to the developer on `18081`, `18082`, and `18083`.

Role journeys

4. How roles move through the protocol flow

A

Seller publishes catalog

  1. The seller announces an actor through `/api/v1/seller/announce`.
  2. The seller creates or updates a product and offer.
  3. Morpheus writes protocol events to the catalog room.
  4. Synapse delivers the events back through AS transactions.
  5. The backend validates the events and updates catalog projections.
B

Buyer creates order

  1. The buyer selects an offer from the local catalog projection.
  2. The backend creates the private order room itself, without a client-supplied room id.
  3. Seller and arbiter AS users are invited into the room.
  4. After joins complete, the backend publishes `customer.bound` and `order.created`.
  5. The `202 Accepted` response contains the real Matrix `room_id`.
C

Seller closes the lifecycle

  1. The seller backend lazily joins the order room before publishing.
  2. It publishes `order.accepted`.
  3. It creates a payment intent, then records authorization/capture.
  4. It publishes an entitlement grant.
  5. It completes the order through `order.completed`.
The practical product path is documented separately for UI, CLI, and HTTP API: UI journey, CLI journey, API journey.

Configuration

6. Instance configuration

A Morpheus server is described by a TOML config. Local single-server runs use `config/local.toml`; federation E2E uses `config/e2e/books.toml`, `config/e2e/cases.toml`, and `config/e2e/fashion.toml`. OIDC local SSO uses `config/local-oidc.toml`.

Section Purpose Important fields
[instance] Marketplace instance identity and protocol capabilities. instance_id, matrix_server_name, catalog_room_alias, order_room_alias_prefix
[appservice] Connection between Morpheus and the Synapse Application Service. homeserver_url, sender_localpart, homeserver_token, appservice_token
[database] Runtime storage for raw events and projections. url
[admin] / [auth] Bind address, bearer token env names, or OIDC session settings. bind, MORPHEUS_ADMIN_TOKEN, MORPHEUS_SELLER_TOKEN, MORPHEUS_BUYER_TOKEN
[[allowlist.instances]] Local trust policy for remote instances. status, capabilities, catalog_room_alias, morpheus_url
[payments.evm_escrow] Optional ERC-20 escrow adapter and watcher configuration. enabled, chain_id, rpc_url_env, escrow_contract, confirmations 
cargo run -p morpheus-cli -- config validate --config config/local.toml
cargo run -p morpheus-cli -- synapse registration \
  --config config/local.toml \
  --out .local/synapse/morpheus-registration.yaml

Single server

7. Run one local server

Postgres and pgweb

docker compose up -d postgres pgweb

Postgres is available on `localhost:5432`; pgweb is available at `http://localhost:8081`.

Synapse bootstrap

mkdir -p .local/synapse
docker run --rm \
  -v "$PWD/.local/synapse:/data" \
  -e SYNAPSE_SERVER_NAME=localhost \
  -e SYNAPSE_REPORT_STATS=no \
  matrixdotorg/synapse:latest generate

After generation, add the registration file to `.local/synapse/homeserver.yaml`.

Database migration

cargo run -p morpheus-cli -- db migrate \
  --database-url postgres://morpheus:morpheus@localhost:5432/morpheus \
  --database-kind postgres

Server process

MORPHEUS_ADMIN_TOKEN=admin-token \
MORPHEUS_SELLER_TOKEN=seller-token \
MORPHEUS_BUYER_TOKEN=buyer-token \
cargo run -p morpheus-server -- --config config/local.toml

After startup, the API and built-in UIs are available at http://127.0.0.1:8080.

Optional local OIDC SSO

docker compose up -d keycloak
MORPHEUS_OIDC_CLIENT_SECRET=morpheus-local-secret \
MORPHEUS_SESSION_SECRET=dev-session-secret \
cargo run -p morpheus-server -- --config config/local-oidc.toml

Keycloak listens on `http://127.0.0.1:18090`; the dev user is `morpheus-admin` / `morpheus-password`.

Troubleshooting

11. Common problems

Synapse does not send transactions to Morpheus

Check `app_service_config_files`, `homeserver_token`, and `url` in the registration YAML, then verify that the Morpheus container hostname is reachable from the Synapse container.

Order create returns 502

This is the expected hard failure when Synapse cannot create the federated room with invites. Check federation DNS aliases, nginx TLS proxy, CA trust, and `:8448` reachability.

Create order shows pending or projection_timeout

The public API returns submitted immediately after Matrix events are published, while the order projection appears only after AS ingest returns the events. The UI shows pending and polls orders. If the projection does not catch up within the polling window, it reports `projection_timeout`. Check Synapse transaction delivery, AS token, appservice URL, and `/admin/events`.

Order create returns OFFER_WITHDRAWN

The buyer used a stale offer that the seller has already withdrawn. Refresh the buyer catalog and choose the current card. Existing orders on old terms keep their lifecycle, but new orders against a withdrawn offer are rejected.

Seller does not see a remote order

Verify that the seller AS user was invited and joined. During order creation, the backend waits for invited users to join before publishing order events so the timeline reaches the remote server.

Remote catalog does not appear immediately

At this stage, trusted remote catalog visibility is built through the Morpheus peer API indexer. Check the allowlist entry, `morpheus_url`, network reachability, and catalog rebuild. If a peer is temporarily unavailable, the sync report returns `cached` and `REMOTE_CATALOG_UNAVAILABLE`, while buyer discovery keeps the last accepted projections visible.

EVM escrow watcher does not project payment state

Check `GET /admin/evm-escrow/status`, the `MORPHEUS_EVM_RPC_URL` value, the configured `chain_id`, `escrow_contract`, confirmations, and watcher checkpoint. Use `POST /admin/evm-escrow/replay` after fixing RPC or deployment configuration.

EVM wallet action stays pending

Submitted wallet transactions are not final payment state. Refresh buyer or seller orders only after the watcher has verified a finalized contract log. The UI should clear `Deposit submitted` or `Release submitted` only when the projected order status moves to `payment_authorized`, `payment_captured`, or `refunded`.

EVM wallet action fails before submitting

Wrong role wallets, failed chain switches, and user rejection are expected pre-submit failures. The result panel reports `wallet_error`, `chain_mismatch`, or `wallet_rejected`, no escrow transaction is submitted, and the action remains available for retry with the correct wallet.

OIDC login redirects but the UI is still unauthenticated

Check `MORPHEUS_OIDC_CLIENT_SECRET`, `MORPHEUS_SESSION_SECRET`, the redirect URL `http://127.0.0.1:8080/auth/callback`, and the Keycloak role plus actor claims imported from `config/oidc/keycloak/morpheus-realm.json`.
