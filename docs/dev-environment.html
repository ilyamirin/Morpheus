Developer setup

A local network of three Morpheus marketplace servers.

This environment starts books, cases, and fashion instances with separate Synapse, Postgres, and Morpheus runtimes. It lets a developer observe the full path: product publication, federated catalog visibility, purchase, order room, seller lifecycle, admin projections, and error diagnostics.

Purpose

2. What this developer setup is

`make e2e-three-synapse` starts a local federation network that is not a pure mock: seller writes go through the Morpheus API, Matrix publisher, Synapse, Application Service ingest, protocol validation, and Postgres projections. The dev runtime still uses the `mock` payment adapter by default, while remote catalog visibility is currently built by a trusted Morpheus peer API indexer. Order flow uses real backend-owned Matrix order rooms.

Three independent instances

`books.example`, `cases.example`, and `fashion.example` have separate configs, DBs, Synapse homeservers, and Morpheus servers.

One Docker network

Containers communicate through service DNS. Federation domains resolve to nginx TLS proxies, not directly to Synapse.

Verifiable seed

The script seeds 14 sellers, 28 products, 28 offers, and one cross-instance completed order.

Real UI/API/CLI

The same backend is available through `/ui/*`, HTTP endpoints, and the `morpheus` CLI.

Runbook

3. Start, check, and stop

Start the full federation network

make e2e-three-synapse

The command generates Synapse configs and a local CA, builds the Morpheus image, starts containers, waits for readiness, checks federation smoke, runs the demo seed, and verifies projection counts.

Quickly check that services are alive

curl -fsS http://127.0.0.1:18081/readyz
curl -fsS http://127.0.0.1:18082/readyz
curl -fsS http://127.0.0.1:18083/readyz

Each endpoint should return `{"status":"ready"}`.

Stop and remove E2E data

make e2e-three-synapse-down

This runs `docker compose -f docker-compose.e2e.yml down -v` and removes Synapse sqlite files from `.local/e2e/synapse-*`. Docker build cache is intentionally left intact.

The final line of a successful run is `three-synapse e2e ok`. Before it, you should see `federation smoke ok (...)` and `demo seed ok`.

Browser surfaces

6. UI workspaces: where to go and what to check

In local/E2E mode, the UI uses a bearer token entered in the input and stores it only in `localStorage`. Production UI can use OIDC SSO and an HttpOnly `morpheus_session` cookie without browser bearer tokens. E2E placeholders are `admin-token`, `seller-token`, and `buyer-token`. The UI does not issue backend secrets.

Role URL Token What to check
Admin /ui/admin admin-token Health, readiness, config JSON, allowlist, catalog/order/payment/entitlement counters, validation stream.
Seller /ui/seller seller-token Storefront cards, optional cover upload, quick add listing, seller orders, per-order Accept -> Intent -> Capture -> Grant -> Complete.
Buyer /ui/buyer buyer-token 28 seeded offers, unique product images, checkout sheet, order tracking, cancel while valid.

UI customer journey

7. Product path in the UI: publish, buy, lifecycle, withdraw

S

Seller publishes a product

  1. Open http://127.0.0.1:18081/ui/seller.
  2. Confirm the `seller-token` token or enter your own seller bearer token.
  3. Optionally upload a cover image. The UI compresses it in the browser and adds it to product media metadata.
  4. Fill title/category and price/currency.
  5. Click `Publish listing`: the UI activates the seller, saves the product, and publishes the offer in one action.
  6. After projection refresh, the card appears in the storefront and buyer catalog.
B

Buyer purchases

  1. Open http://127.0.0.1:18081/ui/buyer.
  2. Click `Refresh catalog`; the UI reads seller/product/offer projections.
  3. Click `Buy` on an offer. Checkout receives offer id, amount, and currency from the projection.
  4. Click `Create order`: `POST /api/v1/buyer/orders` has no editable `room_id`.
  5. The backend creates a private Matrix order room, invites seller/arbiter AS users, and returns the real `room_id`.
  6. Until AS projection arrives, the UI shows submitted/pending state and refreshes orders automatically.
  7. The buyer orders panel shows the created/accepted/payment/entitlement/completed timeline.
L

Seller closes the lifecycle

  1. Open the seller UI for the instance that owns the seller id.
  2. Open the `Orders` tab. There is no top-level manual order id form; use buttons inside the specific order card.
  3. Click `Accept` on the target card: the seller backend lazily joins the order room before publishing.
  4. On the same card, click the next available step: `Intent`, then `Capture`.
  5. Then click `Grant`: the entitlement grant event records external access or a license reference.
  6. Click `Complete`: the order becomes completed, the purchased offer is automatically withdrawn from future sales, and admin counters update.
W

Seller withdraws an offer

  1. In the seller storefront, click `Withdraw` on the offer card or run `seller offer withdraw` through CLI/API.
  2. Return to /ui/buyer; the catalog refreshes automatically, or click `Refresh catalog` if needed.
  3. The offer should disappear from discovery for new buyers.
  4. If a buyer opened a stale card and clicks `Create order`, the backend returns `409 OFFER_WITHDRAWN`.
  5. Open /ui/admin and check auto-refresh counters/events; `rebuild catalog` is only needed for manual reindexing.
  6. Already-created orders are not rewritten: they continue their lifecycle under the fixed terms/hash.
  7. This distinction matters: withdrawal affects future catalog discovery, not past trades.
E

EVM escrow wallet path

  1. Run `make e2e-evm-escrow` to start Anvil, deploy the Vyper escrow, launch Morpheus with EVM escrow enabled, and exercise the local flow.
  2. For an EVM escrow order, the seller card uses `/api/v1/seller/orders/{order_id}/evm-escrow/payment-intent` to create deposit instructions.
  3. The buyer wallet action calls approve and deposit through viem, then shows `Deposit submitted` until the embedded watcher projects authorized payment state from finalized logs.
  4. After watcher confirmation and order refresh, the buyer card shows `Escrow funded` and removes the deposit action.
  5. The seller can release escrow; the seller card shows `Release submitted` until watcher evidence projects `Payment captured`, then removes the release action.
  6. The admin/arbiter wallet can refund or partially refund from the admin UI, with submitted transactions treated as pending evidence until watcher confirmation.
  7. Wrong role wallets, wrong chains, and rejected wallet requests are shown as UI errors without submitting custody-changing transactions.
  8. Use `GET /admin/evm-escrow/status` and `POST /admin/evm-escrow/replay` to inspect or replay watcher indexing.
Cancellation and withdrawal mean different things. Buyer cancel is valid only before payment/entitlement/completion. Seller offer withdraw removes the offer from future catalog discovery, but already-created orders continue under their fixed terms/hash. In the UI this is observable: after withdrawal, buyer catalog no longer shows the offer, while direct stale order create receives `409 OFFER_WITHDRAWN`.
The remote catalog indexer is resilient to temporary trusted-peer unavailability. If a peer API does not respond, the sync report is marked `cached` with `REMOTE_CATALOG_UNAVAILABLE`, and buyer discovery continues to show the last successfully accepted projections instead of an empty catalog.

Runtime internals

10. How it works internally

01UI / CLI / HTTP clientrole token + JSON request
02Morpheus APIactor scope, DTO validation, state prechecks
03Matrix publishercatalog room or backend-owned order room
04Synapse federationroom membership, remote invites, AS transactions
05Protocol validationenvelope, authority, event-specific body, lifecycle order
06Postgres projectionscatalog, orders, payments, entitlements, admin counters
Secrets do not enter Matrix events: payment secrets, bearer URLs, credentials, license keys, and delivery files stay outside `io.marketplace.*`. Protocol events use references, hashes, and evidence metadata.

Troubleshooting

11. Developer setup diagnostics

Docker build downloads Rust dependencies again

The first build after the cache feature still warms the cache. Later builds use BuildKit cache mounts for Cargo registry/git/target. Cache is reset by `docker builder prune`, `docker system prune`, or Docker Desktop cleanup.

Order create returns 502

Check federation proxies, DNS aliases `books.example`, `cases.example`, `fashion.example`, TLS CA trust in Synapse, and whether remote AS users can be invited and joined.

Catalog does not show remote products

Check allowlist capabilities `catalog` and `indexing`, `morpheus_url` in `config/e2e/*.toml`, peer Morpheus API reachability from the container, and `POST /admin/catalog/rebuild`.

UI shows 401/403

401 usually means the bearer token is wrong for the role. 403 `ACTOR_FORBIDDEN` means the actor id does not belong to the local instance, for example when a books seller endpoint receives `seller:fashion.example:*`.

EVM escrow watcher is stale

Check `GET /admin/evm-escrow/status`, `MORPHEUS_EVM_RPC_URL`, the deployed escrow address, token config, confirmations, and watcher checkpoint. After fixing the config or RPC endpoint, run `POST /admin/evm-escrow/replay`.

OIDC session is missing after login

Check the Keycloak container, `MORPHEUS_OIDC_CLIENT_SECRET`, `MORPHEUS_SESSION_SECRET`, redirect URL `http://127.0.0.1:8080/auth/callback`, and the imported role/seller/customer claims.
